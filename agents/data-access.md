# Data Access Rules

適用於涉及資料庫查詢、ContextProcedures、EF Core、SP／Function、資料庫整合的 Explore、Propose、Apply、Verify、Review、SQL 與 System Design；其他任務不套用。

## 前置檢查

1. 先讀 Project 的資料庫總索引，確認本次涉及的資料庫、Schema、Context 與相關索引；以 Project AGENTS.md 記載的位置為準。
2. 讀相關 ContextProcedures（含介面與實作）、參數、Result 定義，再追到對應 SP／Function 本體與必要 Table／View。無此層時依實際來源標示不適用。
3. 核對呼叫順序、權限、篩選、關聯鍵、資料粒度、NULL、狀態、彙總與交易邊界；列出資料庫呼叫次數及回傳範圍，未知項目標記待確認。
4. 依證據決定：沿用既有方法 → 評估相依端後最小修改 → 使用可於資料庫完成的 EF Core 查詢 → 說明既有能力不足後新增 SP。
5. 未完成相關來源檢查前，不得自行新增 SP、改用 EF Core 或以多次查詢拼接結果。缺少索引時僅搜尋本次相關來源；缺少程式或 SQL 本體時列出缺漏及受阻判斷，不補造結論。

MD 只負責定位；實際程式與 SQL 是判定依據。不同資料庫的同名物件必須以資料庫識別、Schema、物件名稱區分，Context 與資料庫不假設一對一。

## 效能阻擋條件

- 同一資料庫內可直接完成的關聯、必要篩選與彙總，不得拆成多個 SP／EF 查詢，再於 C# Join、補欄位或彙總成同一結果集。
- 禁止迴圈內逐筆資料庫查詢、SP 呼叫及權限補查；須批次處理且保留完整授權條件。
- 禁止取回完整候選後才於 C# 篩選指定單號、單元、日期或分頁；條件應傳入資料庫查詢。
- 禁止過早 ToList／ToListAsync／AsEnumerable，再對可由資料庫完成的資料做補查或拼接。
- 多個 SP 本身不直接判定為缺陷；先區分必要命令、獨立結果集與可合併的中間查詢。把多次查詢包進一個 SP 或平行執行，不代表已改善。
- EF Core 與 SP 適用相同規則；最小修改不能作為保留禁止模式的理由。Service 中的必要業務計算仍依既有責任分層，不因本規則全部搬入 SQL。

已證實的禁止模式在設計／Review 列為必修，未修正不得判定通過；來源不足列為待確認，不宣稱已通過，也不虛報量測成本。

## 多資料庫整合

- 先核對資料庫與 Context 對應，以及現有跨資料庫查詢能力、權限與部署條件；不能只因多個 Context 就視為可直接 JOIN。
- 必須由 Service 整合時，記錄無法在資料庫直接關聯的原因、來源／目標、關聯鍵、呼叫順序及交易／一致性策略。
- 限定範圍、批次取資料，禁止逐筆補查；不得為合併查詢擅自新增 Linked Server、權限或分散式交易。
- 跨資料庫取資料與本地交易邊界需明確，不假設單一 Context 交易涵蓋其他資料庫。

## 文件同步與完成條件

- 在產生、重新產生或修改資料存取程式的同一變更中，更新所屬資料庫 MD 索引；跨資料庫流程異動再更新流程文件。
- 記錄方法新增／移除、參數、Result、來源位置與呼叫端變更，保存來源版本與核對狀態；未確認事項標記待確認。
- MD 獨立於自動產生的 C# 檔，不能插入自動產生區或使用過期描述代替來源。
- 設計記錄預計查詢次數；驗證按需求量測實際呼叫次數、回傳筆數與耗時，核對權限、粒度、NULL、狀態及計算結果。無環境時明列未執行及原因。
- 索引與來源不一致必須修正；純分析或 Review 不擅自改檔，將不一致列為 Findings，授權修改後再同步。

文件格式與驗收案例見 Playbook 的 docs/Data_Access.md；實際專案索引存放於 Project，不包含帳密、Token、完整 Connection String 或正式資料。
