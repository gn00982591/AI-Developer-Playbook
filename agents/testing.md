# Testing Rules

適用於 Build、Test 與變更驗證。

## 規則

- 先執行與變更直接相關的最小驗證範圍。
- 必要時再擴大到完整 Build / Test。
- 不因小幅修改自動執行與需求無關的大型測試流程。
- 驗證失敗時，先確認是否與本次 Change 有直接關係。
- 回報實際執行的命令、成功/失敗結果與尚未驗證項目。
- 不把「未執行測試」描述成「測試通過」。

依適用的[開發資安主題](../docs/security/README.md)驗證正常與拒絕情境。按變更測試失敗後的行為或核對發布產物；分開記錄本機模擬、目標環境實測及未執行項目。

涉及資料存取時，另套用 [Data Access Rules](data-access.md)，沿用同版本已核對的索引與來源，只補讀本次直接相依內容。

涉及前端或集中語系資料來源驗證時，依 [前端共用元件與語系](frontend.md) 核對適用案例。 Snapshot 優先載入同名規則，缺少時從已安裝的 Playbook 補讀。

## 驗收證據

- 依 Engine 或 Lightweight 方案的驗收驗證；按需核對需求、Tasks、實作與結果一致性。
- Engine 文件檢查、Build / Test 與資料驗證分開記錄，彼此不替代。
- 純文件或圖表變更驗證來源、引用及一致性，不強制無關 Build / Test。

## 驗證紀錄與接續

在既有紀錄逐項填寫檢查對象、情境、環境、實際執行身分、命令或操作、預期、實際結果、證據位置及限制。按需分列文件檢查、型別／建置、回歸、隔離 SQL、模擬 UI、本機整合、使用者驗收及正式環境驗證。

可重現的失敗比對變更前基準，記錄原始錯誤、重跑條件、結果及根因狀態。調整輸出目錄、測試資料或啟動模式時，在同一紀錄標明差異。

需要他人接手時，先列下一個具體動作、負責人、已核實的入口或對象、所需檔案或查詢條件，以及完成判定。說清是補新資料、重處理既有資料、修改設定或程式，還是單純驗證。現有授權內可完成者直接執行。驗收時抽一份紀錄，確認接手者能重現主要檢查、辨識環境與覆蓋範圍，並執行下一步。
