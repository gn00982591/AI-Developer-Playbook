# 資料存取與多資料庫索引

本文件定義資料存取前置檢查、專案 MD 索引及同步流程。強制規則集中於 [Data Access Rules](../agents/data-access.md)，不建立新的頂層 Preset 或 Stage。

## 1. 執行順序

1. 讀 Project AGENTS.md，取得索引位置。
2. 讀總索引，確認本次資料庫、Schema、Context 與跨資料庫範圍。
3. 讀各資料庫相關索引，定位 ContextProcedures、介面／實作與 Result 檔案。
4. 讀實際參數、Result、SP／Function 本體及必要 Table／View，核對權限、篩選、關聯鍵、粒度與交易。
5. 決定沿用、最小修改、EF Core 完整查詢或新增 SP；記錄理由與預計呼叫次數。
6. 檢查效能阻擋條件，完成程式及文件同步，再驗證結果與查詢成本。

索引不存在時，不全面掃描 Repository；先搜尋本次相關 Context 與入口。來源未提供時列出具體檔案／資料庫物件及受阻判斷。沒有 ContextProcedures 的技術棧，依實際資料存取介面定位並標記不適用。

## 2. 文件位置與責任

以下位置是實際 Project 的預設慣例。已有正式索引時沿用，在 AGENTS.md 記錄入口，不另建同義文件。

| 層級 | 預設位置／命名 | 責任 |
| --- | --- | --- |
| 專案總入口 | docs/data-access/README.md | 列出資料庫用途、Context 對應與各索引連結 |
| 各資料庫索引 | docs/data-access/databases/；檔名依已確認的資料庫識別建立 | 該資料庫的 Procedure、Function、Result、Table／View 與來源位置 |
| 跨資料庫流程 | docs/data-access/flows/；依實際流程識別命名 | 記錄跨資料庫呼叫、資料傳遞、整合與一致性 |

每個資料庫使用穩定的專案識別；實際名稱依專案文件政策記錄。Context 與資料庫分別建對應列，可多對多；同一資料庫的多個 Context 不建立重複物件目錄。

Playbook 只保存規則與格式；實際資料庫物件、Context 路徑與公司業務資訊留在所屬 Project。正式索引不存於會被重建的 .ai-rules/ 或一次性 .ai-output/。

## 3. 索引格式

### 專案總入口

至少記錄以下欄位，使用實際值，不產生假資料列：

| 欄位 | 要求 |
| --- | --- |
| 資料庫識別／用途 | 可區分不同來源；用途由已讀來源確認 |
| Context 類別／原始檔位置 | 分別列出每項實際對應 |
| 連線設定名稱 | 僅設定鍵，不記錄帳密或完整 Connection String |
| 各資料庫索引連結 | 可定位該資料庫文件 |
| 跨資料庫流程連結 | 有涉及才列 |
| 來源版本／最後核對日期／狀態 | 可用 Commit 或檔案雜湊；未取得標記待確認 |

### 各資料庫索引

按業務功能分節，AI 只讀本次相關節，不要求每次載入全部物件。方法清單至少包含：

| 欄位 | 要求 |
| --- | --- |
| 功能／資料庫識別／Schema／物件名稱 | 不以方法名稱推測業務語意 |
| Context／Procedure 方法 | 指向實際介面與實作；非 Procedure 依實際介面記錄 |
| 參數／Result 型別與檔案位置 | 記錄型別、NULL、輸出參數及多結果集；沒有則明列 |
| SP／Function／Table／View 來源位置 | 已讀的 SQL 檔或可核對的物件定義版本；沒有本體標記待確認 |
| 呼叫端 | 檔案與方法；依相關搜尋證據，不猜測全部使用端 |
| 權限／篩選／回傳粒度／關聯鍵 | 註明來源，未知標記待確認 |
| 來源版本／核對日期／狀態 | 區分已核對、待確認與已移除 |

不要複製整份自動產生的 C# 或 SQL 到 MD；索引保存定位與必要摘要。移除方法保留簡短異動紀錄及原因，不保留看似仍可使用的過期入口。

### 跨資料庫流程

至少記錄：實際入口、來源／目標資料庫與 Context、呼叫順序、關聯鍵、傳遞欄位、批次範圍、直接關聯或 Service 整合的依據、交易邊界、一致性與失敗處理、權限及來源版本。

同名 SP 使用資料庫識別＋Schema＋物件名稱定位。不能因資料庫名稱不同，就自行建立 Linked Server 或假設可以使用分散式交易。

## 4. 產生與同步步驟

1. **產生前：**讀現有索引與相關來源，確認資料庫／Context 對應及這次變更範圍。
2. **產生時：**由相同來源擷取方法、參數、Result 與檔案位置，同步建立或更新所屬資料庫索引。語意、權限與粒度須另讀 SQL 本體核對。
3. **重新產生後：**比對方法新增／移除、簽章、Result 欄位及來源位置，不在自動產生的 C# 區塊內寫文件。
4. **整合異動時：**同步更新總入口對應與相關跨資料庫流程；保留其他資料庫的既有內容。
5. **完成前：**核對相對連結、來源版本與待確認項目；程式與 MD 一起納入同一變更／Commit。

這是完成條件與工作步驟，尚未提供 EF Core Power Tools 自動掛鉤或索引生成器；不得宣稱已自動串接。只有生成的方法目錄已核對、SQL 未提供時，方法簽章可標記已核對，業務語意仍標記待確認。

## 5. 設計、實作、審查與驗證

| 階段 | 要求 |
| --- | --- |
| Explore／System Design | 定位來源、還原順序與資料粒度，不修改專案程式 |
| Propose | 評估既有能力與必要相依端，說明查詢方式、次數與跨資料庫策略 |
| Apply／SQL | 執行已確認最小修改；避免 N+1、廣泛取回後篩選及可合併查詢的 C# 拼接，同步索引 |
| Review | Diff 優先，只補讀直接相依來源；已證實的禁止模式列必修，資料不足列待確認 |
| Verify | 核對結果、權限與一致性；依風險量測次數、筆數與耗時，清楚標記未執行 |

多個 SP 不一律禁止：必要命令與獨立結果集先依實際流程判斷。禁止的是可合併卻拆開的資料取得。EF Core 也必須在實體化前完成資料庫可處理的關聯、篩選、彙總與分頁。Service 的必要業務計算保留既有分層。

跨資料庫無法直接關聯而必須由 Service 整合時，記錄原因，限定範圍且批次取得，保留明確的一致性與錯誤處理。把多次查詢包進單一 SP、平行查詢或改用 EF Core，不構成通過依據。

## 6. 驗收案例

以下為規範驗收條件；不是已執行的業務測試。

| 編號 | 條件 | 預期結果 |
| --- | --- | --- |
| DA-001 | 既有 Procedure 完整符合需求 | 查完參數、Result、SQL 本體後沿用，不另造查詢 |
| DA-002 | 同資料庫可直接關聯，卻多次查詢後由 C# 拼接 | 設計／審查列必修，修正前不通過 |
| DA-003 | 候選筆數增加，逐筆補查權限或明細 | 判定禁止模式；改為完整授權的批次檢查 |
| DA-004 | 指定單一計算單元 | 條件在資料庫完成，不取完整候選再篩選 |
| DA-005 | 多資料庫／多 Context／同名 SP | 可由總入口定位正確來源；必要 Service 整合有理由、批次範圍與一致性策略 |
| DA-006 | 重新產生方法，參數或 Result 改變／移除 | 同一變更更新所屬索引與必要流程，來源連結不失效 |
| DA-007 | 索引過期、SQL 缺漏或無驗證環境 | 明列待確認／未執行與受阻事項，不補造語意或宣稱通過 |
| DA-008 | NULL／停用／無權限成員、不同狀態、重量缺漏及金額尾差 | 優化後仍符合原業務規則，無重複列或加總放大 |

涉及實際 SQL 或效能驗證時，由 Project 使用真實測試條件；Playbook 不保存正式資料或公司程式碼。
